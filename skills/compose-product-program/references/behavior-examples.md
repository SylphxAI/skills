# Compose Product Program Behavior Examples

These examples record route intent and artifact oracles. They do not prove that
a particular native host selected the package.

| Request | Expected behavior |
| --- | --- |
| “Coordinate design, API, payments, localized assets, store release, support, and operations for this mobile launch.” | Select this skill and produce one owner map, acyclic dependency graph, handoff tests, release order, and completion decision. |
| “Implement the accepted sign-in capability in this repository.” | Do not select this skill as the primary method; use the authentication or product implementation owner. |
| “Is this shared search layer a standalone product, platform substrate, or connector?” | Use `compose-product-portfolio`; the question is product-unit topology. |
| “Plan and then implement this one accepted retry fix to a ready PR.” | Use `drive-to-delivery`; one objective does not need a cross-domain program artifact. |
| “幫我將設計、付款、素材、上架同客服串成一個有 owner 同 dependency 嘅交付計劃。” | Select this skill; preserve the Cantonese request while returning the repository's expected artifact language. |

## Artifact oracle

A valid Product Program Brief names the objective and terminal, one canonical
owner per material fact, a selected capability matrix, an acyclic dependency
graph, versioned producer/consumer handoffs with acceptance tests, collision
boundaries, recovery, external authority gates, truthful delivery layers, and
one next owner action for every incomplete item. It does not duplicate sibling
truth or create a generated control plane.
