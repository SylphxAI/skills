# Design Review Solicitation Policy

Define when a product may present a native public-review request while keeping
eligibility neutral, voluntary, and independent of product benefits.

## Method

1. List each platform, storefront, territory, audience, product surface, and
   meaningful-value event in scope.
2. Retrieve the current first-party policy and native review API documentation
   for every platform. Record the publisher, applicable section, retrieval time,
   supported surface, quota behavior, presentation rules, and audience limits.
3. Define neutral eligibility from verified meaningful value and a stable
   product context. Apply the same rule across sentiment, payer status, spend,
   tier, private feedback, complaint history, and likely rating.
4. Define a request lifecycle from eligible context through scheduling, native
   invocation, platform-controlled presentation, cooldown, and renewed
   eligibility under current policy.
5. Keep money, rewards, access, remedies, support, referrals, warranties,
   appeals, accounts, data rights, and product flow independent of review state.
6. Use the platform's native surface and neutral product wording. Preserve help
   and private-feedback access in every request state.
7. Record the policy revision, eligibility reason, value event, audience
   decision, attempt time, native result when available, and cooldown.
8. Test the lifecycle across eligible, suppressed, expired-policy, offline,
   accessibility, child-mode, purchase, support, incident, and recovery states.

Read [platform policy and request state](references/platform-policy-and-state.md)
for the adapter fields, lifecycle, official policy sources, and acceptance
conditions.

## Output

Return one platform-current solicitation policy with sources, eligibility,
request lifecycle, independence conditions, persisted fields, and tests.
