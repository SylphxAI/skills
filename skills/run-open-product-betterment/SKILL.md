# Run Open Product Betterment

Treat one active product as a living responsibility when the user has invited
autonomous opportunity selection across an open frontier. Improve it from
current product and user truth, carry sequential coherent batches to their
requested terminals, and re-scout instead of stopping at the first easy
checkpoint. A named bug fix, capability build, finish pass, or accepted
objective belongs to its narrower owner unless the user has also opened this
frontier.

## Method

1. Bind one product, its declared North Star if one exists (otherwise its
   current product promise and selected user outcome), primary users, important
   journeys, repository and product owners, requested terminal, constraints, and
   current source / CI / release / deploy / live state. Treat chat, stale
   backlogs, and cached artifacts as inputs, not authority.
2. Scout current product and user truth: inspect the relevant source, contracts,
   recent work, support or behavioral signals, live readback available to the
   task, and unresolved dependencies. Separate observations, inferences, and
   unknowns.
3. Admit one coherent high-value batch. Use `select-next-work` only when an
   authoritative backlog and claim mechanism exist; otherwise rank opportunities
   within this loop without inventing a tracker. State the user-facing outcome
   and done condition, and include every independent correct action that
   completes that outcome. Rank without a backlog by direct user value,
   urgency, leverage, feasibility, reversibility, and lifecycle cost. Fence
   only the exact edge owned by an external blocker; continue safe independent
   work.
4. Execute at the owning layer. Hand a dependent accepted batch to
   `drive-to-delivery`, while this skill retains re-scout and next-betterment
   ownership. Preserve one semantic owner. Do not add a workaround,
   compatibility or dual-authority path, unfinished migration, technical-debt
   donation, or a second control plane to make the batch appear complete.
5. Run the changed product path and repair defects found there. If the request
   and available authority include landing, release, or deployment, carry that
   state through the owning native lane; otherwise label the result as a
   candidate and name the next owner. Verify the strongest state actually
   reached; do not turn a green check, commit, upload, release request, deploy,
   or HTTP response into a stronger source, CI, release, deploy, or live claim.
6. Self-review every material batch before claiming its terminal. Check for:
   workaround or fallback concealment; compatibility shims or dual writers;
   unfinished predecessor migration; technical debt donated to another owner;
   product or repository boundary violation; and source / CI / release / deploy
   / live truth-layer conflation. Correct the finding or route it to its real
   owner; do not create a central gate or proof pack.
7. Commission an independent challenge through `analyze-critically` for any
   P0, customer-live, money, security, public-contract, destructive, or
   cross-project slice when an independent reviewer is available. Give the
   reviewer the question, evidence, leading conclusion, alternatives, and
   rejection conditions; an author's self-review is not independent challenge
   evidence. Treat the result as decision evidence, not a completion gate. If
   no independent reviewer is available, state that gap honestly with its owner
   and resume predicate, then continue unrelated safe work.
8. Use `write-high-signal-update` for the primary result. When the caller
   requests an Owner-facing typed update, keep it to this one compact result:
   state North Star movement when a trusted measure exists (otherwise
   `unknown`); explicit local/candidate/landed source state, CI check, released
   artifact, deployed target, and live readback states; each dependency owner
   and resume predicate; honest residuals; and the next re-scout action. Do
   not create a separate report, tracker, gate, or proof pack. Keep
   role-specific addresses and task IDs outside the portable skill.
9. Reinspect current product and user truth after the batch and select the next
   bounded improvement while material in-scope opportunities remain. Do not
   silently turn a standing open-frontier run into one fixed objective or stop
   after one batch. Close only when its terminal is true or safe in-scope
   alternatives are exhausted and new authority is required.

## Selection discipline

- Prefer changes that materially improve a real user path or remove a current delivery constraint.
- Keep product and platform responsibilities with their existing owners.
- Complete one coherent outcome before opening another conflicting write set.
- Use current product facts and plain reasoning to explain priority.
- Record external dependencies where they can be resumed by their owner.
- Preserve the product's declared North Star when one exists; do not mint a
  second one for the betterment run.
- Treat the batch review and primary update as decision communication, not an
  activity metric, qualification gate, or new governance system.

## Completion

An open betterment run finishes when a fresh inspection finds no higher-value
in-scope improvement or the requested terminal is true. Return the delivered
batch, changed paths run, challenge status or honest reviewer gap, strongest
truthful delivery state, primary update, and remaining externally blocked
opportunities.

## Boundaries

- This skill owns the open-ended betterment loop and selection of each coherent
  batch. It does not own product strategy, the North Star, implementation
  semantics, CI, release, deployment, live systems, or another product's work.
- `select-next-work`, `drive-to-delivery`, `analyze-critically`, and
  `write-high-signal-update` remain the canonical owners for their independent
  jobs; use them rather than copying their procedures here.
- Do not add a central gate, proof/evidence control plane, activity counter,
  installer, compatibility layer, or generated catalog to make this loop
  portable.
